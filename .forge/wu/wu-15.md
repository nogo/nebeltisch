# Add player ping marker

## Outcome

Any participant (GM or player) can click-and-hold on the map to place a temporary "ping" marker visible to all participants. The ping appears as an animated ring at the clicked location, persists for ~3 seconds, then fades out. Multiple pings can be active simultaneously. Pings are broadcast over WebSocket — all connected clients see them.

## Values

1. Unobtrusiveness — pings are visual-only, no sound, no modal. They appear and fade without requiring dismissal.
2. Simplicity — single gesture (long-press), no dedicated button, no UI chrome.
3. Visibility — ping must be clearly visible at any zoom level against both revealed map and fogged areas.

## Context

- `public/js/canvas.ts` — manages the canvas stack (map, fog, preview). The preview canvas (`previewCanvas`) is currently used only for the GM brush preview circle. Pings should render on a separate overlay or reuse the preview canvas. Since pings are temporary and non-interactive, a dedicated ping layer is cleaner.
- `public/js/gm.ts` — pointer events on `eventTarget` (fogCanvas). Long-press detection must not conflict with fog drawing. A long-press (~500ms hold without move) on the canvas triggers a ping instead of drawing.
- `public/js/player.ts` — pointer events are on the token canvas. Long-press on empty area (not on own token) triggers a ping.
- `public/js/viewport.ts` — (from wu-09) provides `screenToImage()` for coordinate conversion at any zoom/pan level.
- `src/ws/handler.ts` — WebSocket message handlers. Needs a new `ping` message type that broadcasts to all clients in the adventure.
- `src/ws/messages.ts` — message parsing. Needs the new type.
- `public/css/style.css` — ping animation can be CSS (if using DOM elements) or canvas-based. Canvas-based is simpler given the existing architecture.

## Requirements

### 1. Ping layer module (`public/js/ping.ts`)

Create a module that manages a canvas layer for ping markers:

```typescript
interface PingController {
  // Add a ping at image coordinates with a participant's color
  addPing(x: number, y: number, color: string): void;
  // Call on requestAnimationFrame to update animations
  tick(): void;
}

function initPingLayer(wrapper: HTMLElement, getImageSize: () => { w: number; h: number }): PingController
```

- Creates a canvas (position absolute, pointer-events none, same stacking as other layers — above fog, below token).
- Sized to match image dimensions (same pattern as other canvases).

**Ping animation:**
- Ring expands outward from center over 3 seconds.
- Start: small ring (radius ~10px image coords), full opacity.
- End: larger ring (radius ~40px), opacity 0.
- Ring stroke: 3px, color = pinger's token color (or accent blue for GM).
- Optional: add a brief filled circle flash at the start (~200ms) for impact.
- Use `requestAnimationFrame` for smooth animation.
- After 3 seconds, remove the ping from the active list.

**Rendering:**
- On each `tick()`, clear canvas, redraw all active pings at their current animation state.
- If no pings are active, skip rendering (no unnecessary work).

### 2. Long-press detection (gm.ts and player.ts)

Implement a long-press gesture (~500ms hold without significant movement):

- On `pointerdown`: record position and start a 500ms timer.
- On `pointermove`: if pointer moves more than 5px from start position, cancel the timer (user is drawing/dragging, not pinging).
- On timer fire: this is a long-press. Send a `ping` message with image coordinates and the participant's color. Cancel any drawing/dragging that may have started.
- On `pointerup` before timer: cancel timer, proceed with normal interaction.

**GM-specific:**
- Long-press triggers ping, short press/drag triggers fog drawing.
- The ~100ms touch grace period from wu-09 (viewport) fires first. Long-press timer starts after the viewport has determined this is a 1-finger interaction.
- GM ping color: accent color `#4a4aff`.

**Player-specific:**
- Long-press on empty area (not on own token) triggers ping.
- Long-press on own token should NOT trigger ping (it's a drag).
- Player ping color: the player's chosen color.

### 3. WebSocket ping message

New message type for ping broadcast:

**Client → Server:**
```typescript
{ type: 'ping:map', x: number, y: number, color: string }
```

**Server → All clients (broadcast including sender):**
```typescript
{ type: 'ping:map', x: number, y: number, color: string, name: string }
```

Server handler in `src/ws/handler.ts`:
- Both GM and player roles can send `ping:map`.
- Server adds the sender's name to the broadcast (GM → "GM", player → their `playerName`).
- Broadcast to the adventure topic. Also send back to the sender (so their own ping renders via the same path).
- No persistence — pings are ephemeral, not stored in DB.

Add `ping:map` to the message parser in `src/ws/messages.ts`.

### 4. Ping reception (gm.ts and player.ts)

Both GM and player register a handler for `ping:map`:
```typescript
ws.on('ping:map', (msg) => {
  pingCtrl.addPing(msg.x as number, msg.y as number, msg.color as string);
});
```

### 5. Canvas layer integration

In `canvas.ts`, expose the wrapper element (already done via `getWrapper()`) so the ping layer can be attached.

The ping canvas should be inserted between the fog canvas and the token canvas in the stacking order. Since all canvases use `position: absolute`, the DOM order determines stacking. Insert the ping canvas after the preview canvas but before the token canvas.

Alternatively, the ping module creates its own canvas and appends it to the wrapper. It should be appended after `initCanvas()` but before `initTokenLayer()` in both gm.ts and player.ts. Or append after token layer but use a higher z-index — simpler since it doesn't require changing initialization order.

### 6. Cleanup on map switch

When the map switches (`map:switched` handler), clear all active pings. Call a `clear()` method on the ping controller.

## Constraints

- `bun run build` must pass.
- Do not modify files outside the Modifies and Creates lists.
- Do not modify the token drag behavior — long-press on own token must still start a drag, not a ping.
- Pings must not interfere with fog drawing, token dragging, or pan/zoom.
- No sound effects, no haptic feedback (keep it visual only).
- Ping coordinates are in image space — they stay correct across zoom/pan changes.

## Failure Modes

- **Long-press conflicts with fog drawing**: GM holds for 400ms then moves — draws fog AND pings. Detection: long-press, then move slightly. Fix: once long-press timer fires, cancel any drawing state and prevent further draw events until pointer-up.
- **Pings invisible on dark fog**: dark-colored player ping on black fog. Detection: ping on a fully fogged area. Fix: add a white outline or glow to the ping ring (`shadowBlur`).
- **Animation janks at high zoom**: ping at 5x zoom renders a huge ring. Detection: zoom in, long-press. Fix: ping radius should be in screen pixels (constant visual size), not image pixels. Convert using viewport scale.
- **Rapid pings flood the WebSocket**: user spam-clicks. Detection: hold and release repeatedly. Fix: rate-limit to 1 ping per second per client (client-side throttle).

## Verification

```bash
bun run build
```

Manual:
- GM long-presses on map: animated ring appears, visible to all connected players.
- Player long-presses on empty area: ring appears with their color, visible to GM and other players.
- Ping fades out after ~3 seconds.
- Long-press on own token starts drag, not ping.
- Normal fog drawing (GM) and short clicks are not affected.
- Zoom to 3x, ping — ring is a reasonable visual size.
- Switch maps — old pings are cleared.
