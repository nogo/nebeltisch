# Build player frontend and token system

## Outcome
A player opens a join link, enters their name and picks a color, and sees the active map with fully opaque fog. As the GM reveals areas, the fog disappears in real-time. The player sees their own token (colored circle with name) and can drag it around the map. Other players' tokens are visible and update in real-time. The player cannot modify fog or switch maps. `bun test` exits 0.

## Values
1. Responsiveness — fog reveals and token movements appear instantly.
2. Clarity — player sees only what's revealed, nothing else.
3. Simplicity — minimal UI, no controls beyond token dragging.

## Context
- `public/js/canvas.ts` — canvas rendering module from wu-05. Reuse for player view with modifications (fully opaque fog instead of semi-transparent).
- `public/js/websocket.ts` — WebSocket client from wu-05. Extend with `connectPlayer()`.
- `public/js/api.ts` — API client from wu-05. Reuse `getAdventureByPlayerLink`.
- `src/ws/messages.ts` — message types. Player receives: `joined`, `fog:stroke`, `fog:stroke:batch`, `fog:reset`, `token:moved`, `token:added`, `token:removed`, `map:switched`, `player:joined`, `player:left`.
- `src/ws/handler.ts` — server-side WS handlers. Token creation on player connect, deletion on disconnect already implemented in wu-04.
- WebSocket connects to `/ws?adventureId=...&role=player&playerLink=...&playerName=...&playerColor=...`.

## Creates
- `public/player.html` — player interface page.
- `public/js/player.ts` — player client-side logic.
- `public/js/tokens.ts` — token rendering and drag interaction module (shared between GM and player views).

## Modifies
- `public/js/canvas.ts` — add option for fully opaque fog (player mode) vs semi-transparent (GM mode). Add method to render tokens on the canvas.
- `public/js/websocket.ts` — add `connectPlayer()` function.
- `public/index.html` — ensure join flow links to player page correctly.

## Requirements

### 1. Player page (`public/player.html`)
Minimal layout:
- **Top bar:** Adventure name, player's own name and color indicator.
- **Main area:** Canvas (full screen minus top bar). No sidebars, no tools.
- No upload, no brush, no image gallery. Player is a viewer + token mover only.

### 2. Player join flow
From `public/index.html`, player enters:
- Player link code (from the adventure's share link)
- Their name (text input)
- Their color (color picker input, default to a random color)

On submit: validate via `GET /api/adventures/join/:playerLink`. If valid, redirect to `player.html#adventureId=...&playerLink=...&name=...&color=...` (URL fragment).

On player page load: parse fragment, connect WebSocket with player credentials.

### 3. Player canvas
Reuse `CanvasController` from `public/js/canvas.ts` with a `mode` option:

- `mode: 'gm'` — fog color `rgba(0, 0, 0, 0.85)` (semi-transparent, GM can peek)
- `mode: 'player'` — fog color `rgba(0, 0, 0, 1.0)` (fully opaque)

Player canvas has no pointer events for fog interaction — brush events are disabled.

### 4. Token rendering (`public/js/tokens.ts`)
Tokens are rendered on a third canvas layer on top of the fog canvas.

Each token:
- Filled circle with the player's color, radius ~20px (fixed screen size, does not scale with zoom).
- Player name drawn below the circle in white text with dark outline for readability.
- Own token has a subtle highlight ring (2px white border).

Module exports:
- `initTokenLayer(container: HTMLElement, canvasWidth: number, canvasHeight: number): TokenController`
- `TokenController.addToken(token: { id, name, color, x, y }): void`
- `TokenController.removeToken(tokenId: string): void`
- `TokenController.moveToken(tokenId: string, x: number, y: number): void`
- `TokenController.enableDrag(tokenId: string, onMove: (x, y) => void): void` — enables drag interaction for the player's own token.
- `TokenController.render(): void` — redraws all tokens.

Token positions are in image-space coordinates. Convert to screen coordinates for rendering using the same scale factor as the fog canvas.

### 5. Token drag interaction
On the token canvas layer:
- `pointerdown` on own token (hit test: distance to token center < radius) → start drag.
- `pointermove` while dragging → update token position locally, send `token:move` via WebSocket. Throttle to max 30/s.
- `pointerup` → end drag, send final position.

Other players' tokens are not draggable.

### 6. WebSocket integration for player

**On `joined`:**
- Load map image from `/uploads/:filename` for the active image.
- Apply fog mask from the `fogMask` field (base64 → Uint8Array → render on fog canvas).
- Render all tokens from the `tokens` array.
- Enable drag on own token (matched by `tokenId` from join response — extend `joined` message to include `yourTokenId`).

**On `fog:stroke` / `fog:stroke:batch`:**
- Apply stroke(s) to local fog canvas using `CanvasController.applyStroke()`.

**On `fog:reset`:**
- Full mask replace — `CanvasController.applyFogMask()`.

**On `token:moved`:**
- `TokenController.moveToken()` for the moved token.

**On `token:added`:**
- `TokenController.addToken()`.

**On `token:removed`:**
- `TokenController.removeToken()`.

**On `map:switched`:**
- Load new map image, apply new fog mask, re-render tokens.

**On `player:joined` / `player:left`:**
- Optional: show a brief toast notification. Keep it minimal.

### 7. GM view token integration
Update the GM frontend (from wu-05) to also render tokens. The GM sees all tokens and can observe player movements but does not own a token.

Import and initialize `TokenController` in `public/js/gm.ts`. On `joined`: render existing tokens. Handle `token:added`, `token:moved`, `token:removed` messages.

### 8. Extend `joined` server message
In `src/ws/handler.ts`, the `joined` message sent to players must include `yourTokenId: string` so the client knows which token is theirs for drag interaction.

## Constraints
- `bun test` must pass (no regressions).
- No npm dependencies.
- Player fog is fully opaque — no peeking.
- Players can only drag their own token.
- Token rendering must not interfere with fog canvas interaction on GM side (separate canvas layer).
- Do not modify server-side files outside the Modifies list unless strictly required.
- Token canvas must be transparent except for the tokens themselves.

## Failure Modes
- **Token appears under fog:** Token canvas must be above fog canvas in z-order. Detection: manually verify token visible on revealed area.
- **Drag moves wrong token:** Hit test must check closest token owned by this player. Detection: test with multiple tokens close together.
- **Coordinate drift:** If token positions use different coordinate space than fog strokes, tokens appear in wrong places. Detection: place token on a revealed landmark, verify alignment.
- **Player sees fogged area flash:** If map image loads before fog mask is applied, briefly shows full map. Prevention: apply fog mask synchronously before making canvas visible, or start with canvas hidden.

## Verification
```bash
bun run build:client
bun test
```
Manual: open GM in one browser, player in another. GM reveals area → player sees it. Player drags token → GM sees movement. Second player joins → first player sees new token.
