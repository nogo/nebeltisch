# Fix fog layer for WebP and unsupported image formats

## Outcome

When a GM uploads a WebP image (or any non-PNG/JPEG format) and switches to it, the fog layer is fully opaque — the map is hidden behind black fog, exactly like PNG and JPEG maps. The GM can then reveal areas normally.

## Values

1. Correctness — every uploaded image gets a working fog layer regardless of format.
2. Minimal change — fix the dimension parsing gap; don't rearchitect the upload pipeline.

## Context

- `src/routes.ts` lines 20-48 — `parseImageDimensions` parses PNG and JPEG headers but returns `{width: 0, height: 0}` for WebP (and all other formats). This is the root cause.
- `src/routes.ts` line 262 — upload handler calls `parseImageDimensions` and stores the result. WebP gets stored with 0x0 dimensions.
- `src/ws/handler.ts` lines 25-41 — `getFogMaskForImage` calls `repairImageDimensions` when dimensions are 0, but `repairImageDimensions` also uses `parseImageDimensions` so it can't fix what it can't parse.
- `src/ws/handler.ts` line 38 — `createMask(image.width, image.height)` creates a 0x0 mask for WebP images.
- `public/js/canvas.ts` lines 119-143 — `applyFogMask` receives the 0x0 mask. It falls back to loaded image dimensions for w/h but the decompressed pixel data is empty (0 bytes). It then calls `putImageData` with an all-transparent ImageData, which clears the fog that `loadImage` → `fillFog()` had just drawn.

## Requirements

### 1. Parse WebP dimensions

Extend `parseImageDimensions` to handle WebP files. WebP has three encoding variants inside a RIFF container:

- **VP8** (lossy): bytes at offset 26-29 contain width (16-bit LE, lower 14 bits) and height (16-bit LE, lower 14 bits). The VP8 bitstream starts after the "VP8 " chunk header. The frame header has 3 bytes of frame tag, then 3 bytes of start code (0x9D 0x01 0x2A), followed by width (2 bytes LE) and height (2 bytes LE).
- **VP8L** (lossless): after "VP8L" chunk tag + 4-byte size + 1-byte signature (0x2F), the next 4 bytes encode width-1 (14 bits) and height-1 (14 bits) in a bitstream.
- **VP8X** (extended): bytes at offset 24-26 contain (width-1) as 24-bit LE, bytes 27-29 contain (height-1) as 24-bit LE.

Detection: file starts with "RIFF" (bytes 0-3) and "WEBP" (bytes 8-11).

The implementation must handle at least VP8X (the most common for modern WebP files) and VP8. VP8L is a bonus but not required.

### 2. Fallback for still-unknown formats

If `parseImageDimensions` still returns 0x0 (unknown format), `repairImageDimensions` should use a browser-free approach to get dimensions. Since Bun doesn't have a DOM, the simplest robust fallback is to shell out to a tool or use the image file's actual bytes.

A simpler alternative: in `getFogMaskForImage`, if the mask dimensions are still 0x0 after repair, do NOT create a 0x0 mask. Instead, skip the mask entirely (return a mask that won't be sent), so the client's `fillFog()` from `loadImage` remains intact. This means: if `image.width === 0 || image.height === 0`, throw or return a flag that tells the caller to send `fogMask: null`.

## Constraints

- `bun run build` must pass.
- Do not modify files outside the Modifies list unless strictly required.
- The fix must not break PNG or JPEG dimension parsing.
- Do not add external dependencies for image parsing.

## Failure Modes

- **VP8X parsing off-by-one**: WebP VP8X stores (width-1) and (height-1). Forgetting to add 1 gives wrong dimensions. Detection: upload a known-size WebP and log the parsed dimensions.
- **Mask still 0x0 for unknown formats**: If fallback isn't implemented, unknown formats still get no fog. Detection: the `getFogMaskForImage` path must handle 0x0 gracefully by not sending a mask that clears the fog.
