# Make tokens persistent and add player management

## Outcome

Tokens persist across disconnects and reconnects. Opening the same player link in a second tab reuses the existing token instead of creating a duplicate. The GM can remove a player (deleting their token) via a new WebSocket message. Players who reconnect see their token where they left it. The GM receives a player roster with online/offline status.

## Values

1. No data loss — tokens survive disconnects, browser crashes, and server restarts.
2. Identity = player link — same link always maps to the same token within an adventure.
3. GM control — only the GM can remove players. Players cannot delete their own or others' tokens.

## Context

- `src/ws/handler.ts` — `handleWsUpgrade()` (line 66-126): creates a new token on every player connection via `createToken()` (line 108). `close()` handler (line 291-315): deletes the token on disconnect via `deleteToken()` (line 308). Both must change.
- `src/db/tokens.ts` — `createToken()` always inserts a new row. Needs a `findOrCreateToken()` that checks for existing token by `(adventure_id, player_link)` first. `deleteToken()` stays for GM removal.
- `src/db/schema.ts` — tokens table has unused `player_session_id TEXT NULL` column (line 36). Repurpose as `player_link TEXT NULL` to link tokens to player identity.
- `src/types.ts` — `Token` interface (line 35-43) and `WsData` interface (line 46-52). Token needs `player_link` field. WsData needs `playerLink` field.
- `src/ws/connections.ts` — `ConnectionInfo` (line 4-10) tracks connected clients. Needs `playerLink` field. `getConnectionsForAdventure()` (line 37-43) already exists — useful for building the player roster.
- `src/ws/messages.ts` — needs new message types: `player:remove` (client→server, GM only), `player:roster` (server→client, sent on join and on status changes).
- `public/js/gm.ts` — needs to receive and track the player roster for the upcoming UI (wu-12).
- `public/js/player.ts` — needs to handle being removed (redirect to home or show message).

## Requirements

### 1. Schema migration — add player_link to tokens

In `src/db/schema.ts`, rename the `player_session_id` column to `player_link` (or add a migration that adds `player_link TEXT NULL` and drops `player_session_id`). Since this is a PoC with no production data, a simple schema change is fine — drop and recreate the table if needed, or use `ALTER TABLE` to rename.

Add a UNIQUE constraint on `(adventure_id, player_link)` to prevent duplicate tokens per player per adventure.

### 2. Token find-or-create (`src/db/tokens.ts`)

Add a function:
```typescript
export function findOrCreateToken(
  db: Database,
  { adventureId, playerLink, name, color }: {
    adventureId: string;
    playerLink: string;
    name: string;
    color: string;
  }
): Token
```

Logic:
1. Query: `SELECT * FROM tokens WHERE adventure_id = ? AND player_link = ?`
2. If found: update name and color (player may change these between sessions), return existing token.
3. If not found: insert new token with `player_link` set, return it.

Keep existing `createToken()` for backward compatibility but it should not be used for player connections anymore.

### 3. Update Token type (`src/types.ts`)

Add `player_link: string | null` to the `Token` interface.

### 4. Update WsData and ConnectionInfo

In `src/types.ts`, add `playerLink?: string` to `WsData`.

In `src/ws/connections.ts`, add `playerLink?: string` to `ConnectionInfo`.

### 5. Token reuse on connect (`src/ws/handler.ts`)

In `handleWsUpgrade()`, replace the `createToken()` call (line 108) with `findOrCreateToken()`:

```typescript
const token = findOrCreateToken(db, {
  adventureId,
  playerLink,
  name: playerName,
  color: playerColor,
});
tokenId = token.id;
```

Pass `playerLink` into `WsData`.

### 6. Do NOT delete token on disconnect

In the `close()` handler, remove the `deleteToken()` call (lines 307-309). Instead:
- Broadcast `player:left` with the player name (keep existing behavior for presence indication).
- Do NOT broadcast `token:removed` — the token persists.

### 7. Do NOT broadcast token:added on reconnect

In the `open()` handler, the current code broadcasts `token:added` for the connecting player's token (lines 168-176). This is wrong for reconnecting players — their token is already known to other clients from the `tokens` array in the `joined` message.

Change: only broadcast `token:added` if the token was newly created (not reused). `findOrCreateToken()` should indicate whether the token is new. If new → broadcast `token:added`. If reused → broadcast `player:joined` only (presence update, not token creation).

### 8. Player roster message

Add a new server→client message type:
```typescript
interface PlayerRosterMessage {
  type: 'player:roster';
  players: Array<{
    tokenId: string;
    name: string;
    color: string;
    online: boolean;
  }>;
}
```

Send `player:roster` to the GM:
- On GM connect (in the `joined` message, or as a separate message immediately after).
- Whenever a player connects or disconnects (so the GM sees live presence updates).

Build the roster by:
1. Get all tokens for the adventure from DB.
2. For each token, check if there's an active connection with that `tokenId` in the connections map.
3. Set `online: true/false` accordingly.

### 9. GM player removal (`player:remove`)

New client→server message:
```typescript
interface PlayerRemoveMessage {
  type: 'player:remove';
  tokenId: string;
}
```

Handler in `src/ws/handler.ts`:
1. Validate GM role.
2. Find the token in DB, verify it belongs to this adventure.
3. Delete the token from DB.
4. If the player is currently connected (check connections map by tokenId), close their WebSocket with a reason.
5. Broadcast `token:removed` to all clients.
6. Send updated `player:roster` to GM.

Add the message type to `src/ws/messages.ts`.

### 10. Player removal handling (client-side)

In `public/js/player.ts`: when the WebSocket closes unexpectedly or receives a close reason indicating removal, show a message: "You have been removed from this session." with a link back to the home page. Do not auto-reconnect after removal.

In `public/js/gm.ts`: handle the `player:roster` message — store the roster in state for the upcoming UI (wu-12). For now, just store it; the UI rendering will come in wu-12.

### 11. Player link in join URL flow

The player join URL currently includes `name` and `color` as hash params. On reconnect, the player may use the same URL (bookmarked). The server should accept these and update the token's name/color if they've changed.

No changes needed to `public/js/player.ts` URL parsing — it already reads `name` and `color` from the hash. The server's `findOrCreateToken()` handles the update.

## Failure Modes

- **Duplicate token on race condition**: two tabs open the same player link simultaneously, both call `findOrCreateToken()` before either's insert commits. Detection: open two tabs at exact same time. Fix: the UNIQUE constraint on `(adventure_id, player_link)` causes one insert to fail — catch the constraint violation and retry with a SELECT.
- **Stale tokens accumulate**: players who never return leave tokens in the DB forever. Detection: check token count after many sessions. Acceptable for PoC — future cleanup could expire tokens older than N days.
- **GM removes player who is mid-drag**: token deleted while player is dragging. Detection: remove player during active drag. Fix: player's WS gets closed, drag stops naturally.
- **Player reconnects with different name/color**: token's name/color update but other clients show stale data. Detection: rejoin with different name. Fix: broadcast `token:updated` or include updated token in `player:joined`. Simplest: include the token data in the `player:joined` broadcast so clients can update.
